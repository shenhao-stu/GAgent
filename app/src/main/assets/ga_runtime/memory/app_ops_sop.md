# App 操作 SOP — 常用 App 快而准（约束账本 · 登录墙 · 只读纪律）

> 目标：让任意能力的模型都能**迅速且不丢约束**地操作常用 App（搜索/筛选/排序/浏览）。
> 依据：AndroidDaily 基准复盘（`projects/androiddaily_bench/REPORT.md`）——头号失败是**多约束丢失**（约束数 3+ 成功率 0%），其次是登录墙阻断与只读越界。
> 与 `phone_use.md` 的关系：**动作 API 签名以 droid.py docstring 为准, 用法节奏与坑见 `phone_use.md`**；本文件只加"任务级纪律"，不重复也不覆盖那里的 API。

---

## 第一性原则：把约束"外化"成账本，不靠记性

弱模型丢约束的根因＝把"要满足哪些条件"留在脑内（易随长轨迹遗忘）。解法＝**开局就把任务解析成一份显式约束账本，每步只对照账本核销，账本全绿才算完成**。这是不变量，不是建议。

### Step A｜解析任务 → 约束账本（动作前必做）

把用户一句话拆成结构化账本（写进 `update_working_checkpoint`，让它随轨迹持续可见）：

```
constraints = {
  "app":     "<目标 App 或 '未指定'>",
  "keyword": "<搜索词>",
  "filters": ["品牌=罗技", "价格<=500", "内存=16GB"],   # 逐条, 缺一不可
  "sort":    "销量降序 | 价格升序 | 最多播放 | None",
  "readonly": true,   # 搜索/浏览/查看类=只读; 下单/发布/支付=写(需用户确认)
  "goal_page": "<终态: 如'商品结果列表页且筛选+排序已生效'>"
}
```

> 不变量：**账本条目数 = 用户提出的条件数**。TB-02 失败＝账本漏了"价格上限"；TB-03＝"品牌"中途掉了。宁可多列一条，绝不少列。

### Step B｜逐约束执行 + 即时核销（一步一验）

每完成一个约束 → **重新观察（shot/dump）确认它真的生效** → 在账本打勾 → 再做下一个。

```
for c in constraints.filters + [sort]:
    施加 c（点筛选/选项/排序）
    重新 shot()/dump() 观察          # 不假设点了就生效
    if c 已在界面体现:  账本[c] = ✅
    else:               重试一次; 仍失败→记 ❌ 并如实报告, 不谎报完成
```

> 关键：筛选/排序类操作**点击 ≠ 生效**（很多 App 需再点"确定"或有防抖）。必须回看界面确认（如"已选:罗技""综合↓变销量↓"高亮）。

四条实测教训（AndroidDaily v3 三模型 24-rollout 复盘，全模型踩坑）：

1. **筛选面板必须以"确定"收口**：选中筛选项后停在面板里 ≠ 完成；点"确定"回到结果页、且结果页出现筛选 chip/标签才算生效。（TB-02：三个模型全部漏此步或未成）
2. **数值型筛选走自定义输入框**：预设区间不含目标值时（如淘宝价格区间只有"80~329/329~904"而任务要"≤500"），在"最低价/最高价"自定义框逐位输入数字→收键盘→确定→回看结果页验证；输入后必须回读框内文本确认数值完整（实测出现"50"截断）。
3. **搜索框占位词陷阱**：搜索框灰色占位词（如"笔记本电脑"）不是你的输入；不确认框内实际文本==目标关键词就点搜索，会搜出占位词结果（违反"不得进入错误关键词结果"负向约束）。发起搜索前必须回读输入框内容。
4. **终态自检**：宣称完成前重新 shot 确认**当前屏幕**就是账本 goal_page——"过程中做到过"不算，排序/筛选态会因回退/重进/刷新而丢失（B-01：三个模型过程中都切过排序，终态全部回退到默认排序）。

### Step C｜完成判据（账本全绿才 done）

```
done ⟺ keyword 已搜 ∧ 每个 filter ∈ ✅ ∧ sort 已确认 ∧ 停在 goal_page ∧ 未违反 readonly
```

任一未满足 → 未完成，继续或如实说明卡点。**禁止"做了一部分就宣布完成"。**

## 登录墙：早探测、即停手、不自动登录（安全红线）

真机真账号下，很多 App（京东/小红书/淘宝部分入口）在搜索前/后弹登录/验证码/绑定。基准里 XHS-01、JD-01 即因此阻断，且观察到 agent 自行发起微信授权登录——**这是红线**。

```
launch(app) → 首屏先 shot()/ui_detect 找拦截信号:
  登录 / 注册 / 验证码 / 绑定手机 / 授权登录 / 一键登录 / 微信登录 / 短信验证
若命中且挡住目标:
  ① 立即停止自动化, 不点任何登录/授权按钮
  ② 不输入账号/验证码, 不走第三方(微信/QQ/Apple)授权登录用户账号
  ③ 告知用户"该 App 需要你先登录, 登录后我继续", 交回控制权
```

> 判据：登录墙属**环境前置**，不是能力失败。如实报告"被登录墙阻断"，不绕道、不谎报。

## 只读纪律：搜索/浏览/排序/筛选 = 绝不写

只读任务里禁止：点进并**播放**视频、下单/加购/支付、发帖/评论/点赞/关注、私聊发消息。B-01 的失败之一就是误点播放了无关视频。

```
只读任务中每次 tap 前自问: 这一点会不会触发播放/写入/跳转离开结果页?
  会 → 除非任务显式要求, 否则不点; 找"不触发写"的等价路径(如只滚动浏览、只读取文字)
```

## 迅速：批量观察，减少冗余截图

"快"不是跳过验证，而是**同一帧把该拿的坐标一次拿齐**再连续动作：

```
shot() 一次 → ui_detect 收齐本步所有目标 bbox(搜索框/关键筛选/排序入口)
           → 按序 tap(不必每次 tap 后都重新截图)
           → 到"约束核销点"才重新观察验证(见 Step B)
```

- dump 可用（非敏感 App、树非空）→ 优先 dump 拿节点坐标，比视觉快且稳。
- dump 空/敏感 → 走 shot+ui_detect（敏感清单=`droid.SENSITIVE_APPS` 注册表; 注册 App 前台 `droid.dump()` 恒返回 `[]`=敏感置空信号, 直接转视觉, 勿当空壳树重试; 见 `phone_use.md`）。
- 中文输入优先 `webcdp.open_url('...?q=中文')` 或 `droid.paste`，避免逐键（见 `phone_use.md`）。

## 原生优先（strict）vs 网页兜底

基准 strict 口径要求**在原生 App 内**完成。默认走原生 App；仅当原生被登录墙/反爬彻底挡死且任务允许时，才降级 `webcdp`（记为 web 兜底，向用户说明）。纯信息类（比价/查数据）可直接用 `webcdp` 提速——以任务性质为准。

## 一页速查

```
1. 解析任务 → 约束账本(keyword/filters[]/sort/readonly/goal_page), 写 checkpoint
2. launch 后首屏先探登录墙 → 命中就停手报告, 绝不自动登录/第三方授权
3. 逐约束施加 → 每个都回看界面确认生效 → 账本打勾(点击≠生效)
4. 账本全绿 ∧ 停在 goal_page ∧ 没违反只读 → 才算完成; 否则如实说卡点
5. 快 = 同帧批量取坐标连续动作 + 只在核销点重验; dump 能用就用, 敏感/空则视觉
```
